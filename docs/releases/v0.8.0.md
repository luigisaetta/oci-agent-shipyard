# v0.8.0: OCI Agent Shipyard, agents with a database, complete teardown

Release date: 2026-10-21.

## Highlights

### A new name: OCI Agent Shipyard

The project formerly called `codex-4-oci-enterprise-ai-deployment` is now
**OCI Agent Shipyard**: the repository, the recommended folder of the tool
home, and the Conda environment are all called `oci-agent-shipyard`
([Spec 025](../../specs/025-rename-to-oci-agent-shipyard.md)). The skill
names (`oci-agent-*`), the manifests, and existing Hosted Applications do not
change. GitHub redirects the old address; to align a workstation, follow
[Migrating to OCI Agent Shipyard](../migrating-to-oci-agent-shipyard.md).

### Agents with a managed Oracle database

An agent can now keep data between requests in an Oracle Autonomous Database
that the service creates and connects to the application: no database,
wallet, network, or credentials to manage.

* **Deploy** ([Spec 026](../../specs/026-managed-adb-storage-at-creation.md)).
  An optional `deploy.storage` section (`type: ADB`) makes the first release
  create the storage, named `<application_name>-storage`, and link it when
  the Hosted Application is created. The agent receives the connect string in
  `DB_CONNECT_STRING` and the credentials as files. The plan shows the
  storage; a rerun reuses an orphaned storage instead of creating another;
  an existing application whose storage differs from the manifest stops the
  deploy, because storage can be set only at creation.
* **Agent code** ([Spec 027](../../specs/027-agents-with-a-database.md)).
  `oci-agent-new` generates agents that load catalogs from packaged files into
  the database at startup, save the records they produce, and read them back
  with `GET` endpoints. New guidelines B9 and B10 (into the specification)
  and Q8 and Q9 (into the code) cover credentials, short transactions, an
  idempotent schema compatible with Oracle Database 19c, additive schema
  changes, and seeding with `MERGE`. The local verification runs without a
  database; the database checks run in the remote verification.
* **Lessons from the first live agent** (Spec 027 amendment), now in the
  guidelines: columns with an `IS JSON` constraint come back already decoded;
  an Oracle reserved word as a bind variable name (`:number`) fails with
  ORA-01745; the database initialization retries in the background and
  `/ready` reports `database_error`; because the container logs cannot be
  read, a 5xx response carries a technical code such as `[ORA-01745]`; and an
  offline test runs one full request with a fake LLM and a fake database.

### Complete teardown: `oci-agent-teardown`

A seventh skill removes an agent completely
([Spec 029](../../specs/029-skill-oci-agent-teardown.md)): the Hosted
Application and its deployment, the managed storage, the OCIR repository with
its images, and the local container images.

* **Plan first.** Every resource is listed with its OCID and action, with the
  warnings that storage data and repository images are lost.
* **Two confirmations.** It deletes only after explicit approval of the plan
  and the typed application name (`--confirm`).
* **Protections.** A repository or a storage used by another application is
  kept; a resource that OCI is still changing stops the teardown; IAM,
  identity domains, Vault secrets, and Generative AI projects are never
  touched.
* **Safe reruns.** A rerun skips what is already deleted and continues.

### Platform dispatch, to prepare OCI AI Data Platform

The tool prepares for skills for a second platform, OCI AI Data Platform
(AI DP), without risk for the existing ones
([Spec 028](../../specs/028-platform-dispatch.md)). Each agent folder's
`AGENTS.md` declares its target platform; every skill reads that declaration
first, then the folder's files, then asks. `oci-agent-new` asks for the
platform when the request does not state it, with the two options. No skill
names an AI DP skill yet.

### Always-valid rules for every code change

The `AGENTS.md` block of each agent folder now also asks Codex to follow the
guidelines' code rules (Q rules) for every change of the agent code, with or
without a skill: Q8 and Q9 for agents with a database.

### Scope made explicit

[UNPLANNED.md](../../UNPLANNED.md) lists the features that the project
deliberately does not plan to support, with what the tool does instead and the
workaround. First entry: private endpoints and custom networking.

## Known limitations

* Managed storage is set only when an application is **created**; deleting
  the application loses its data. The managed database is Oracle 19c (no
  `VECTOR` type).
* The permission that an operator who is not a tenancy administrator needs
  for managed storage is not verified yet.
* The live acceptance of the platform dispatch (Spec 028) and a pass on a real
  Windows workstation are pending.

## Upgrading from v0.7.0

1. If your tool home still has the old name, follow
   [Migrating to OCI Agent Shipyard](../migrating-to-oci-agent-shipyard.md)
   first. Otherwise, `git pull` in the tool home.
2. Install the new skill, then start a new Codex session:

   ```bash
   scripts/install_skills.sh
   ```

   On Windows: `./scripts/install_skills.ps1`.
3. For each existing agent folder, refresh its `AGENTS.md` once, from the tool
   home, to add the platform declaration and the code rules:

   ```bash
   python scripts/agent_instructions.py ensure --target <agent-folder>
   ```

4. To give an existing agent a managed database, release it with a **new
   application name** and `deploy.storage`: storage cannot be added to an
   existing application, and the new application starts with an empty
   database.

Existing agents and Hosted Applications need no change.
